Sequence 1/2: plan → robot, all automatic

Steps 1–4 happen in the web app and end with a Ready plan in CDF. From step 5 nobody touches a keyboard: the bridge polls CDF, downloads the plan and its reference map, sets gbplanner's global bound and publishes everything as latched ROS topics. In the live run, Ready-to-topics took about 7 seconds.

PlanFlyUploadReview09:29

Sequence 2/2: mission → findings → models → review

During the mission the bridge only listens: gbplanner's own topics plus your detection stack's findings. Mission end is detected (homing, then quiet, then still), and the bridge uploads the map, creates the campaign and stores the findings as defect detections (status New). The ROS-launched dss worker builds the 3D models. The inspector reviews, confirms real defects, and Suggestions turns them into the next plan — marking it Ready starts the next mission. Marking the plan Complete only when every task was inspected is the convention the sandbox uses; it's an open question whether you want an InProgress plan state instead (PRD §4.3).

Hardware and environment

Ground station install once

  • ROS 1 Noetic (Python 3.8) for autoassess_bridge
  • uv + Python 3.12 checkout of the AutoAssess SDK for dss worker (one roslaunch autoassess_full.launch starts both)
  • Outbound HTTPS (443) to <cluster>.cognitedata.com and the login provider
  • CDF service-account credentials in a git-ignored .env; uploads need write access
  • Disk for maps and meshes: a single mesh can be 100–270 MB

Drone and sensors derived

  • Localise in the reference map frame of the plan's mapExternalId
  • 3D capture: mesh (PLY, per-vertex RGB) and/or point cloud (PCD)
  • RGB camera with known intrinsics and body→camera extrinsic
  • Pose log at image timestamps (TUM format)
  • UT thickness gauge for ndt_thickness tasks

Accuracy and reviewers from the PRD

  • KO-5: < 1 cm relative accuracy of defect/NDT registration
  • NFR-04: always cloud-connected at upload time, no offline mode
  • NFR-05: reviewers need Chrome/Edge/Firefox with WebGL 2
  • KO-7: demonstrated on bulk carrier, container ship and tanker

Tasks are an unordered set

The drone decides the order. The sandbox uses nearest-neighbour as an example.

Two kinds of task

element: inspect a structural element at its centre point. region: a surface point with outward normal and radius.

Findings go the other way

Publish detections as JSON on /autoassess/findings: {"id","x","y","z","nx","ny","nz","radius","inspection_type","class","confidence","description"} — only x,y,z required. At mission end they become defect detections on the campaign; confirming them turns Suggestions into plan tasks.

This is the whole input. Metres, map frame. Element tasks only carry a centre point, no bounding box (PRD OQ-10), so ask whether a centre is enough to plan a viewpoint. The schema is signed off with WP4/WP7 under OQ-5: this session is the place to object.

Reality check: how do tasks reach the drone?

Confined-space inspection drones such as Flyability Elios 3 and ScoutDI Scout 137 are flown by a pilot. We found no public API for uploading waypoints to either.

  • Elios 3 data goes to Flyability Cloud, which offers REST APIs for the recorded data.
  • Scout 137 tags data to its position on a 3D map and uploads to Scout Portal after flight.
  • So plan.json may be a pilot checklist plus a post-flight import, not an autopilot program. Either way the bridge publishes the plan and reference map, and the post-flight upload is automatic.
Which one is your drone?

A · Autonomous

Your software reads plan.json and calls something like goto(pose) / inspect(). The sandbox's sim_drone is shaped for this.

B · Pilot-flown

Show tasks to the pilot, then convert the vendor export (cloud API, SD card) into the mission folder before dss campaign upload.

Based on public vendor pages only; ask the teams to correct us. Either path ends in the same mission folder, which is why the output contract matters more than the flight interface.

App deployment: how a viewer version reaches users

1 · Deploy a draft

npx @cognite/cli apps deploy uploads the build as a DRAFT of the version in app.json (versionTag). Drafts are invisible to users and open only via a customAppVersion=<tag> link — that's how our PRs link test builds.

2 · Sign

apps sign: a developer signature is required before publishing (dev projects need no certification).

3 · Publish · 4 · Activate

apps publish makes the version visible; apps activate makes it the default for users. Every step is explicit, so a bad build never reaches inspectors by accident.

  • Today: the Reveal viewer (0.1.0-alpha.1) and the Drone Sandbox (0.0.1) are drafts; the active viewer version is untouched.
  • Login once: npx @cognite/cli auth login; deploys then run non-interactively.
  • Quirks we hit: stale .cognite-bundles/ packages get re-uploaded unless deleted; App Hosting rejects archive files (.zip/.bin) — the sandbox embeds Python's stdlib in its worker because of this.
  • Published versions are immutable — bump versionTag per release; drafts may be overwritten.

Answers "how do changes reach the inspectors": PR → draft link for testing → sign/publish/activate when accepted. Nobody tests in production.
